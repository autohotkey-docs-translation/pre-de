Änderungen von v2.0 bis v2.1

Diese Seite enthält eine vollständige Übersicht über alle Änderungen zwischen AutoHotkey v2.0 und v2.1. Änderungen nach v2.1 finden Sie im Änderungsprotokoll. Technische Details zu den Änderungen erhalten Sie auf GitHub.

Hohe Auswirkung

Diese Änderungen können dazu führen, dass v2.0-Skripte im aktuellen Release nicht wie erwartet funktionieren.

Nicht-modale Menüs

Das Tray-Menü und Menu.Show verwenden nun nicht-modale Menüs. Dadurch können neue Threads gestartet werden, ohne dass das Menü einfriert. Die systemseitige Unterstützung für nicht-modale Menüs verursacht einige Bugs in Bezug auf die Z-Reihenfolge und die Möglichkeit, auf den ersten Menüpunkt in einem Untermenü zu klicken. Derzeit sind nicht-modale Menüs standardmäßig aktiviert. Dies kann sich jedoch ändern, wenn keine Lösungen für die Bugs gefunden werden.

Standard-DPI-Sensitivität

Die DPI-Sensitivität verwendet nun standardmäßig "Per Monitor v2" statt "System".

Skripte sind von dieser Änderung nur in bestimmten Szenarien betroffen, wie unter OS-DPI-Skalierung beschrieben. Um die Auswirkungen dieser Änderung zu verstehen, ist ein grundlegendes Verständnis über die DPI-Skalierung erforderlich, insbesondere im Hinblick auf zwei Phänomene, die bei einer DPI-Diskrepanz Auswirkungen auf System-DPI-sensitive Skripte haben:

  • Die Fenster des Skripts werden vom System bitmap-skaliert. Dadurch bleiben GUI-Fenster in der Regel auch bei DPI-Übergängen ohne zusätzlichen Aufwand seitens des Skripts nutzbar. Allerdings erscheinen alle Fenster, die nicht der System-DPI entsprechen, unscharf.
  • Koordinaten werden virtualisiert; das heißt, sie werden auf Basis der System-DPI zwischen physischen Pixeln und einem Koordinatenraum umgerechnet. Virtualisierte Koordinaten sind im Zusammenhang mit den automatisch skalierten Fenstern des Skripts sinnvoll, können jedoch in Skripten, die mit externen Fenstern arbeiten, zu unerwarteten Ergebnissen führen.

Pro-Bildschirm-DPI-Sensitivität deaktiviert die DPI-Virtualisierung und Bitmap-Skalierung und verlangt folglich vom Programm, auf DPI-Änderungen zu reagieren, z.B. durch Größenänderung der GUI und ihrer Steuerelemente. Dies geschieht nun standardmäßig automatisch, es sei denn, das Skript deaktiviert DPIResize für die GUI oder das Steuerelement. Die interne Skalierung ist nicht perfekt und erfordert in manchen Fällen zusätzliche Unterstützung durch das Skript.

Skripte, die mit der neuen Standardeinstellung nicht zurechtkommen, können den bisherigen Modus in einem engeren Kontext wiederherstellen, wie unter DPI-Skalierung: Gemischte Einstellungen beschrieben.

Skripte, die bereits für den Pro-Bildschirm-Modus ausgelegt sind, bleiben wahrscheinlich von dieser Änderung weitgehend unberührt. Bei solchen Skripten wurde möglicherweise bereits beobachtet, dass sich der Modus unter bestimmten Bedingungen unerwartet zurücksetzt. Das liegt daran, dass das Hauptfenster des Skripts erstellt wird, bevor das Skript den Modus setzt. Einzelheiten finden Sie unter DPI-Skalierung: Neue Threads.

Hardcodierte Bildschirmkoordinaten und Offsets müssen für sekundäre Bildschirme möglicherweise angepasst werden. Dies wäre jedoch ohnehin erforderlich, wenn sich die Anzeigeeinstellungen ändern würden.

Kompatibilitätsmodus [v2.1-alpha.29+]

Einige Änderungen am Verhalten des Skripts werden nur aktiviert, wenn mit #Requires eine Versionsanforderung angegeben wird, die von "2.0.x" nicht erfüllt werden kann. Derzeit gibt es zwei Modi: v2.0-Modus und v2.1-Modus. Der Modus kann für jedes Modul und jede Funktion separat festgelegt werden. Einzelheiten dazu, wie die Direktive funktioniert, finden Sie unter Kompatibilitätsmodus (#Requires).

Standardmäßig wird der v2.0-Modus verwendet, was jedoch die Nutzung von Features, die v2.1 erfordern, nicht ausschließt.

Leer-Ungesetzt

Dieser Begriff wird im Zusammenhang mit Eigenschaften und Rückgabewerten verwendet. In v2.0 und bei Rückgabe an einen Aufrufer im v2.0-Modus ist der Wert "" (eine leere Zeichenkette). Wenn eine Fat-Arrow-Funktion einen endständigen Aufruf wie X() => Y() ausführt, kann ein Leer-Ungesetzt-Ergebnis ohne den Vielleicht-Operator (?) propagiert werden. Andernfalls ist es äquivalent zu unset.

Interne Funktionen geben leer-ungesetzt zurück, wenn sie keinen dokumentierten Rückgabewert besitzen.

Folgende Dinge geben leer-ungesetzt zurück, wenn bestimmte Bedingungen erfüllt sind, unter denen zuvor "" zurückgegeben wurde:

  • Array: Delete, Pop, RemoveAt
  • Object: DeleteProp
  • Gui: __Item, FocusedCtrl, MenuBar
  • GuiFromHwnd
  • GuiCtrlFromHwnd
  • InputHook: OnChar, OnEnd, OnKeyDown, OnKeyUp
  • MenuFromHandle
  • ObjGetBase und Base (Any)
  • RegExMatch: AusgabeVar

Standardrückgabe

Wenn das Ende eines Funktionskörpers erreicht ist oder return ohne Parameter verwendet wird, kann die Funktion "" (eine leere Zeichenkette), unset oder leer-ungesetzt zurückgeben.

  • Funktionen im v2.0-Modus verwenden standardmäßig "".
  • Funktionen im v2.1-Modus verwenden standardmäßig unset, wenn return mit einem Parameter irgendwo innerhalb der Funktion verwendet wird.
  • Andernfalls wird standardmäßig leer-ungesetzt verwendet.

v2.0-Modus

Wenn eine Funktion oder Eigenschaft im v2.0-Modus aufgerufen wird und leer-ungesetzt zurückgibt, wird der Rückgabewert in "" (eine leere Zeichenkette) übersetzt.

Siehe auch: Standardrückgabe, Leer-Ungesetzt

v2.1-Modus

Folgende Dinge geben unset zurück, wenn bestimmte Bedingungen erfüllt sind, anstatt einen Fehler auszulösen:

  • Array: __Item, Get
  • Gui: __Item
  • Map: __Item, Delete, Get
  • Object: GetMethod, GetOwnPropDesc

Insgesamt wird unset bei fehlenden Elementen oder Werten konsistenter zurückgegeben. In v2.0 (und im v2.0-Modus) geben einige Methoden oder Eigenschaften hingegen "" zurück, während andere einen UnsetItemError auslösen.

Siehe auch: Standardrückgabe, Leer-Ungesetzt

Geringe Auswirkung

Diese Änderungen sollten die Funktionsfähigkeit von v2.0-Skripten nicht beeinträchtigen, können jedoch das Programmverhalten beeinflussen. Dazu gehören einige Änderungen am Verhalten, das bisher nicht dokumentiert war (auf das sich ein Skript daher nicht hätte verlassen sollen), sowie einige Änderungen am dokumentierten Verhalten, die grundsätzlich keine Anpassungen an bestehenden Skripten erfordern sollten.

InputHook: Wenn man jetzt mit KeyOpt eine Option per Name von einer SC-basierten Taste entfernt, wird die Option auch vom entsprechenden VK entfernt (das Gegenteil war bereits der Fall).

ListVars zeigt ungesetzte Variablen nun als "VarName: unset", anstatt Zeichenkettenlänge und -kapazität anzuzeigen.

MouseGetPos löst nun einen OSError aus, wenn die Mausposition nicht ermittelt werden kann.

RegExReplace kürzt Ersatz nicht mehr beim ersten Nullzeichen (sofern vorhanden).

Wenn das Tray-Menü angezeigt wird, wird der aktuelle Thread nicht mehr blockiert.

#Warn ohne Parameter aktiviert nun VarUnset und Unreachable und deaktiviert LocalSameAsGlobal für das aktuelle Modul, anstatt alle Warnungen zu aktivieren und in den MsgBox-Modus zu wechseln (wie #Warn All, MsgBox).

Es wird nun gewarnt, wenn UTF-8-Dekodierungsfehler in Skriptdateien auftreten.

FensterTitel-Parameter mit zwei unterschiedlichen ahk_id-Werten finden nun nichts, anstatt einen der beiden Werte willkürlich zu ignorieren.

Das in der EXE eingebettete Manifest hat nun disableWindowFiltering, wodurch mehr Fenster erkannt werden können.

Folgende Dinge sind nun nicht-Groß-/Kleinschreibung-sensitiv auf ASCII-Basis, nicht mehr gemäß den aktuellen Sprach- und Regionseinstellungen des Benutzers: Tab-Steuerelement-Methode UseTab (mit Ausnahme des VollNameVergleich-Modus, der bereits ausschließlich ASCII-basiert war), Methode Choose und Eigenschaft Text; Menu-Methode Add.

  • Dies ist nun konsistent mit der Nicht-Groß-/Kleinschreibung-Sensitivität der Namen von Variablen, Eigenschaften und GUI-Steuerelementen.
  • Wenn das Ziel darin besteht, ein zuvor hinzugefügtes Element zu identifizieren, sollte man am besten genau dieselbe Zeichenkette verwenden (was in der Regel auch erwartet wird). ASCII-fremde Zeichen wie "À" müssen in der originalen Groß-/Kleinschreibung angegeben werden. Kanonisch äquivalente Unicode-Sequenzen, die binär nicht äquivalent sind, werden nicht mehr als gleich angesehen, selbst wenn sie identisch aussehen. Ein Beispiel hierfür sind die Zeichen LATIN SMALL LETTER A WITH RING ABOVE (U+00E5) und LATIN SMALL LETTER A + COMBINING RING ABOVE (U+0061 U+030A), die beide als "å" dargestellt werden.
  • Bestimmte Unicode-Zeichen werden bei Vergleichen nun nicht mehr fälschlicherweise ignoriert. Zum Beispiel wurde ein Menüpunktname, der ausschließlich aus den folgenden Zeichen bestand, bisher als Trennlinie (leerer Name) interpretiert: ⮙⮝⮛⮟

Eigenschafts-Setter, die in einer Klasse definiert sind, erlauben nun das Weglassen des value-Parameters (unset), sodass Zuweisungen wie x.y := unset behandelt werden können. Setter, die das nicht berücksichtigen, könnten zunächst mit der Ausführung beginnen und dann bei der value-Auswertung einen UnsetError auslösen, statt sofort beim Setter-Aufruf einen Error auszulösen.

Neue Rückgabewerte

Einige Funktionen, die bisher immer "" zurückgaben (wo nicht dokumentiert), geben nun einen nützlicheren Wert zurück:

HotIf gibt nun den vorherigen Wert von A_HotIf zurück.

Die Methoden ToggleCheck und ToggleEnable von Menu geben nun den neuen Zustand zurück.

Tastatureingabe

Texteingabeerfassung und Behandlung von toten Tasten wurden geändert:

  • Behebt einige obskure Probleme und reduziert das Risiko, dass das aktive Fenster die Behandlung von toten Tasten beeinträchtigt.
  • Tote Tasten mit den InputHook-Optionen S und I haben keinen Einfluss mehr auf die Eingabeerfassung.
  • Die InputHook-Option M ermöglicht nun die Erfassung von Ziffern des Ziffernblocks bei gedrückter Alt-Taste und wirkt sich nicht mehr auf die Alt+nnnn-Eingabe aus, wenn die Zifferntasten unterdrückt sind.
  • Verkettete tote Tasten werden unterstützt, bis zu 3 tote Tasten in Folge.

InputHook behandelt {tote Taste}{BS} nun so, dass BS (Backspace) die tote Taste aufhebt.

Neubelegungen nutzen nun Links-/Rechts-Modifikatoren in Blind; z.B. bewirkt >^a::b, dass RCtrl-A zu B und LCtrl-RCtrl-A zu LCtrl-B umbelegt wird, statt einfach nur zu B.

Ctrl::Alt sendet nun kein ununterdrücktes {Ctrl up} mehr. Dies war ursprünglich dazu gedacht, ein Problem bei der systemseitigen Behandlung der Modifikatortasten zu umgehen, wurde jedoch in v2.0.8 von einem besseren Workaround abgelöst.

Debugger

DBGp-Eigenschaft und Kontextbefehle wurden verbessert:

  • Geerbte Eigenschaften werden direkt dem Eigenschaftselement des Objekts untergeordnet.
  • Eigenschafts-Getter und Funktionsaufrufe erlauben mehrere Parameter.
  • Eigenschaftsnamen können als Parameter verwendet werden.

DBGp verwendet jetzt standardmäßig max_children = 1000 und max_depth = 1.

Der Debugger listet nun Eigenschaften auf, die vom Prototyp für Object-fremde Klassen wie VarRef und ComValue definiert werden, nicht mehr einen hartcodierten (potenziell leeren) Satz von Pseudo-Eigenschaften.

Das Debugger-Attribut "classname" von Prototypobjekten enthält nun den Klassennamen (z.B. "SomeClass.Prototype").

Der Debugger listet die nativ definierten Eigenschaften __Class und Base nicht mehr auf.

Globale, lokale und statische Variablendeklarationen mit mehreren Initialisierern werden nun als einzelner Ausdruck ausgewertet, sodass man beim Debuggen nicht mehr jeden Initialisierer einzeln überspringen muss.

DPI-Sensitivität

Grundlegende Unterstützung für Pro-Bildschirm-DPI-Sensitivität ist nun verfügbar, einschließlich:

  • Automatische Anpassung der Schrift im Hauptfenster des Skripts.
  • Automatische Anpassung der Position, Größe und Schriftgröße von GUI-Steuerelementen.
  • Verwendung der GUI-DPI anstelle der System-DPI bei der Schriftgrößenberechnung.

Einzelheiten finden Sie unter DPIResize (Gui).

Abwärtskompatibel

Diese Änderungen sollten keinerlei Auswirkungen auf v2.0-Skripte haben.

Syntax und Kernobjekte

Module, #Module und #Import sind nun verfügbar.

Funktionsdefinitionsausdrücke werden nun unterstützt.

Der Operator a !~= b ist nun verfügbar, der äquivalent zu !(a ~= b) ist (Kurzform für "nicht RegExMatch").

Typisierte Eigenschaften (Strukturen) werden nun unterstützt.

Funktionen und Eigenschaften können nun unset zurückgeben; das Ergebnis kann mit den Operatoren Vielleicht (?) und Oder-Vielleicht (??) zugelassen bzw. behandelt werden.

Pflichtparameter können nun rechts neben optionalen Parametern definiert werden, z.B. Fn(a?, b).

Optionale Verkettung mit dem Vielleicht-Operator (a?.b) wird nun unterstützt.

Der Vielleicht-Zuweisungsoperator (??=) ist nun verfügbar.

Ladezeitvalidierung für unset, ? und ?? wurde verbessert.

Ein Längenlimit für Parameter-Standardzeichenketten (aber nicht für Ausdrücke) wurde entfernt.

Any.Prototype.Props() und Props sind nun verfügbar, um eigene und geerbte Eigenschaften zu enumerieren.

Virtuelle Referenzen werden nun unterstützt:

  • Jedes Objekt mit einer __Value-Eigenschaft kann als virtuelle Referenz fungieren.
  • Virtuelle Referenzen werden von &ByRef-Parametern, internen Ausgabeparametern und dem Dereferenzoperator (%ref%) akzeptiert.
  • Der Referenzoperator (&) erlaubt interne/virtuelle Variablen.
  • Der Referenzoperator (&) kann mit einer Eigenschaft (ohne Parameter) verwendet werden; z.B. &x.y ruft x.__ref('y') indirekt auf.
  • Object.Prototype.__Ref ermittelt eine verschachtelte Struktur oder PropRef (eine virtuelle Referenz, die auf eine Eigenschaft verweist).
  • VarRef und ComValueRef haben eine __Value-Eigenschaft.

Class.Call akzeptiert nun zusätzliche optionale Parameter, um die dynamische Erstellung von Klassen zu erleichtern. Insbesondere können dadurch Skripte Prototypobjekte dynamisch erstellen, die auf anderen nativen Typen als Object basieren, z.B. Map und Array.

Tastatur und Maus

{Blind} unterstützt nun Links-/Rechts-Modifikatoren, wie in {Blind>^}.

Neubelegungen unterstützen nun WheelUp, WheelDown, WheelLeft und WheelRight auf beiden Seiten.

Automatisch-ersetzende Hotstrings vermeiden nun nach Möglichkeit das erneute Tippen eines identischen führenden Teils.

InputHook unterstützt nun die H-Option, um Hotkeys abzufangen.

Interne Funktionen

ATan2: Neue Funktion.

CallbackCreate: Anstelle der Parameteranzahl kann nun ein Array von Parametertypen angegeben werden.

DllCall: CDecl kann nun weggelassen werden, egal welche Aufrufkonvention die Funktion verwendet.

Edit: Optionaler DateiName-Parameter hinzugefügt.

FileCreateShortcut: Der Tastenkürzel-Parameter erlaubt nun die Modifikatoren ^, + und !.

ImageSearch: X und Y können nun weggelassen werden.

IsSet: Akzeptiert nun beliebige Unset-Ausdrücke. Zum Beispiel: IsSet(X?.Y)

PixelSearch: X und Y können nun weggelassen werden.

ProcessWait: ListLines zeigt nun "STILL WAITING" an, wenn das Warten unterbrochen und dann fortgesetzt wurde, so wie es bereits bei WinWait der Fall war.

RegExReplace: Ersatz kann nun eine Rückruffunktion anstelle eines Ersatztextes sein.

Throw: Nun eine Funktion, für mehr Flexibilität.

TraySetIcon: Aktualisiert nun auch das Symbol im Hauptfenster des Skripts.

Type: Gibt nun die Zeichenkette "unset" zurück, wenn Wert ungesetzt ist. Zum Beispiel: Type(MeineVar?)

WinGetAlwaysOnTop: Neue Funktion.

WinGetEnabled: Neue Funktion.

Interne Variablen

A_KeybdHookInstalled und A_MouseHookInstalled sind nun verfügbar.

A_HotIf ist nun verfügbar.

Interne Klassen

Error: Neue Methode Show.

Gui:

  • Neue Methode OnMessage.
  • Neue Methode SetCue für Edit- und ComboBox-Steuerelemente.

Menu:

  • Neuer Parameter Warten (#3) für Menu.Prototype.Show.
  • Neue Option RTL für Menu.Prototype.Add.

Sonstiges

ahk_class ist nun nicht-Groß-/Kleinschreibung-sensitiv, sofern nicht im RegEx-Modus.

Optimierungen

Diese Optimierungen verbessern die Performanz, haben aber sonst keinen Einfluss auf das Verhalten.

Pause lässt den System-Thread nun schlafen, bis Meldungen eintreffen, statt den Pausezustand häufig abzufragen. In Tests sank die CPU-Auslastung dadurch von 0,04 % auf 0,00 %.

ProcessWaitClose und RunWait lassen den System-Thread nun schlafen, bis das Prozesshandle signalisiert wird oder Meldungen eintreffen. Dies senkt die CPU-Auslastung (wie oben) und verbessert die Reaktionszeit.

Optimierungen bei den Prüfungen von Dialogfensterklassen.

Der ternäre Operator führt keine überflüssige Prüfung mehr durch, ob ein Wert eine Zahl ist.

Optimierungen bei der Suche nach Fenstern; Einzelheiten finden Sie unter FensterTitel - Performanz.
